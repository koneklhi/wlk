# 이번에 한 일 이해하기 — 배포 화면을 백엔드에 붙이기

웹 개발을 잘 모르는 상태에서, 이번 작업에서 무슨 문제가 있었고 어떻게 풀었는지 이해하기 위한 정리다.
용어는 처음 나올 때 쉬운 말과 비유로 풀어 썼다.

## 전체 그림부터

우리 시스템은 크게 두 덩어리다.

- **백엔드**: 파이썬으로 도는 서버. 마이크로 들어온 소리를 글자로 바꾸고(음성인식) 번역까지 하는 실제 두뇌.
  배포 PC에서 계속 켜져 있다.
- **프론트엔드**: 사람이 보는 화면(웹 페이지). 버튼, 자막, 설정 같은 UI. 프론트 개발자가 만들었다.

이 둘은 원래 따로다. 프론트 개발자는 화면만 만들어서 "빌드된 결과물"(dist라고 부른다) 형태로 넘겼다.
이번 작업은 그 화면을 배포 PC에서 실제로 띄우고, 백엔드(두뇌)와 제대로 대화하게 연결하는 일이었다.
붙이는 과정에서 에러가 몇 개 났고 그걸 하나씩 잡았다.

내가 실제로 한 일은 이거다: 화면 파일을 배포 PC에 놓고, 서버를 켜고, 화면에서 나는 에러를 확인해서 전달하고,
고친 백엔드 파일을 USB로 배포 PC에 옮기고, 다시 테스트했다. 에러 원인 분석과 백엔드 수정은 이 대화에서 함께 했다.

## 알아두면 편한 기본 개념

몇 단어만 알면 아래가 훨씬 쉽다.

- **브라우저와 서버**: 브라우저(크롬 등)는 손님, 서버는 가게다. 손님이 "이 페이지 주세요" 하고 요청하면 가게가
  파일을 준다. 이 주고받음이 웹의 전부다.
- **dist(빌드 결과물)**: 프론트 개발자는 React라는 도구로 화면을 만든다. 그대로는 브라우저가 못 읽어서 "빌드"를
  거쳐 브라우저가 읽는 HTML·JavaScript·CSS 파일 묶음으로 바꾼다. 그 묶음이 dist다.
- **서빙(serving)**: 서버가 그 dist 파일들을 브라우저에 나눠주는 것. 이번엔 별도 웹서버 없이 우리 백엔드가 직접
  나눠주게 했다. 그래서 화면도, 음성인식도 같은 주소(localhost:8900)에서 다 처리된다.
- **폐쇄망**: 배포 PC는 인터넷이 끊긴 환경이다. 그래서 뭐든 외부에서 못 받아오고 필요한 건 전부 그 PC 안에
  있어야 한다. USB로 파일을 옮긴 이유가 이거다.

## 겪은 문제와 해결

### 1. 화면이 하얗게만 떴다

처음 열었을 때 아무것도 안 나오고 흰 화면만 떴다. 개발자 도구(F12) 콘솔에 "JavaScript인 줄 알았는데 HTML이
왔다"는 에러가 있었다.

무슨 일이냐면, 화면 파일(HTML)에는 "내 부품(JavaScript)들은 `/wlkies/…` 주소에 있다"고 적혀 있었다. 그런데
백엔드는 그 부품들을 다른 자리에서 나눠주고 있었다. 브라우저가 `/wlkies/…`로 부품을 달라고 하면 백엔드가
엉뚱하게 화면 HTML을 다시 줬다. 브라우저는 "이건 부품이 아니라 그냥 페이지잖아" 하고 멈춰서 흰 화면이 됐다.

여기서 나온 말:
- **base 경로**: 이 화면은 `/wlkies`라는 하위 폴더 밑에 사는 걸 전제로 만들어졌다. 주소 앞에 늘 `/wlkies`가
  붙는다는 뜻.
- **MIME 타입**: 브라우저는 받은 파일이 무슨 종류인지 라벨을 본다. JavaScript를 기대했는데 라벨이 "HTML"이라
  거부한 것.

해결: 백엔드가 화면 파일 안을 읽어서 "이 화면은 `/wlkies` 밑에 사는구나"를 스스로 알아채고, 부품들도
`/wlkies/…`로 정확히 나눠주게 고쳤다. 그러자 화면이 떴다.

### 2. 음성 인식이 안 됐다

화면은 떴는데 말을 해도 자막이 안 나왔다. 콘솔에 "WebSocket 주소 '/asr'가 잘못됐다"는 에러가 있었다.

- **WebSocket**: 보통 웹은 "질문 한 번, 답 한 번"으로 끝난다(편지 같은 것). 그런데 실시간 음성인식은 소리를
  계속 흘려보내고 자막도 계속 받아야 한다. 그래서 끊기지 않는 전화 통화 같은 연결을 쓰는데, 그게 WebSocket이다.
- 프론트는 이 전화를 걸 때 주소를 `/asr`이라는 짧은 줄임말로 적었다. 그런데 배포 PC의 브라우저가 구버전이라
  줄임말 주소를 못 알아듣고 거부했다. 전화 연결 자체가 안 됐으니 소리를 못 보내고 자막도 없었다.

해결: 백엔드가 화면을 내줄 때 작은 보정 스크립트를 끼워 넣어서, 줄임말 주소를 브라우저가 알아듣는 정식 주소
(`ws://localhost:8900/asr`)로 자동으로 바꿔주게 했다. 그 뒤 서버를 한국어·영어 자동감지 모드로 켜니 음성인식과
번역이 됐다.

### 3. 번역 사전 저장이 안 됐다

관리자 페이지에서 단어 대치(예: "6군"→"육군")는 잘 저장됐는데, 번역 단어쌍·문장쌍을 넣으니 저장이 안 되고
콘솔에 404·405 에러가 났다.

- **REST API / 엔드포인트**: 프론트가 백엔드에 뭔가 부탁할 때(단어 추가, 삭제 등) 정해진 주소로 요청한다. 이
  주소 하나하나를 엔드포인트라고 한다. 식당 메뉴판의 각 메뉴 같은 것.
- 프론트가 번역 사전 메뉴를 `/api/corrections/prompts` 주소로 주문했는데, 백엔드의 실제 메뉴 주소는
  `/api/prompts`였다. 주소가 안 맞으니 백엔드가 "그런 메뉴 없다(404)" 또는 "주소는 있는데 그 방식으론 못
  준다(405)"고 답했다.

해결: 프론트를 못 고치는 상황이라, 백엔드가 프론트가 부르는 주소로도 똑같이 답하도록 별칭 주소를 추가했다.
그러자 번역 사전 저장이 됐다.

### 4. 아직 남은 것

두 가지는 프론트 화면 자체의 버그라 백엔드로는 근본적으로 못 고치고, 지금은 우회해서 쓰고 있다.

- **관리자 이동 버튼**: 누르면 주소가 이상하게 만들어져 404가 난다. 지금은 주소창에
  `localhost:8900/wlkies/admin`을 직접 쳐서 들어간다.
- **녹음 중지/재시작 버튼**: 한 번 중지하면 다시 시작이 안 된다. 백엔드는 "연결 한 번에 녹음 한 번" 구조라
  다시 녹음하려면 연결을 새로 열어야 하는데 화면이 그렇게 안 돼 있다. 지금은 새로고침(F5) 후 다시 시작한다.

이 둘은 새 프론트 개발자가 화면 코드를 고쳐야 한다. 그래서 그 사람에게 줄 인계 문서를 따로 만들어 뒀다
(`FRONTEND_HANDOFF_NEXT_DEV.md`).

## 한 줄 정리

이번에 한 일은 "프론트 개발자가 만든 화면을, 백엔드가 제대로 띄우고 대화하도록 연결하고 그 과정의 에러들을
잡은 것"이다.

- 되는 것: 화면 표시, 음성 인식, 번역, 단어 대치, 번역 사전.
- 남은 것: 관리자 이동 버튼, 녹음 재시작 버튼 (프론트 수정 필요, 지금은 우회).

이 과정에서 나온 웹 기본 개념:

- 브라우저(손님) ↔ 서버(가게), 요청과 응답
- dist = 빌드된 화면 파일 묶음, 서버가 그걸 서빙
- base 경로 = 화면이 사는 하위 폴더(`/wlkies`)
- MIME 타입 = 파일 종류 라벨
- WebSocket = 실시간 전화 연결(음성 스트리밍용)
- REST API / 엔드포인트 = 백엔드에 요청하는 주소들
- 404 = 그런 주소 없음, 405 = 주소는 있는데 요청 방식이 틀림
