1. PLC(주기적 언어 감지)가 타당한가 — 왜 4.0초이고, 더 잘게 쪼개면 안 되나
   먼저 오해를 풀어야 합니다: PLC는 "언어를 감지하는 주된 방법"이 아니라, 다른 방법들이 못 잡는 한 가지 경우를 위한 백스톱입니다. 코드에는 언어 감지 트리거가 4개 있습니다:

트리거 코드 언제
최초/eager 감지 align_att_base.py:200 \_detect_language_if_needed 세그먼트 시작 시 1회 (1.5~2.0s 누적 후)
짧은 침묵 후 재감지 backend.py:115 \_check_short_silence_language pause 후 1.5s 재축적 시점
화자 전환 시 backend.py:139 new_speaker (eager) Sortformer가 화자 바뀜 감지
PLC align_att_base.py:228 \_maybe_periodic_lang_check 위 3개가 아무것도 안 터지는 연속 발화
앞 3개는 자연 경계(침묵·화자전환·발화시작)에서 이미 세밀하게 감지합니다. PLC가 담당하는 유일한 케이스는 ytn2 동시통역처럼 "침묵도 화자전환도 없이 발화 중간에 en→ko로 매끄럽게 넘어가는" 상황입니다. 이건 이벤트가 없어서 앞 3개가 절대 못 잡습니다.

"4.0초마다 체크"의 진짜 의미 — 감지 해상도가 아니라 디바운스입니다. 핵심은 체크 간격(4.0s)과 감지 윈도우(2.0s)가 분리돼 있다는 점입니다 (align_att_base.py:237-240):

if audio_end_secs - self.state.last_periodic_lang_check < check_interval: # 4.0s 스로틀
return
new_lang = self.detect_current_language(window_secs=2.0, min_prob=0.90) # 항상 2.0s 윈도우
그래서 "0.1초마다 체크"가 더 정확하지 않은 이유는 세 가지입니다:

0.1초로는 언어를 감지할 수 없습니다. detect_current_language는 최근 오디오 윈도우를 인코더에 통과시켜 Whisper 언어 ID를 돌립니다. 0.1s에는 음향 정보가 거의 없어 결과가 난수에 가깝습니다 — 특히 한·영 혼용 환경에서 한 단어는 어느 언어로도 들릴 수 있습니다. 그래서 윈도우는 어차피 2.0s로 고정입니다. 간격을 0.1s로 줄여도 **"거의 같은 2초 윈도우를 40배 더 자주 재평가"**할 뿐, 0.1s 간격 두 윈도우는 오디오의 95%가 겹쳐 새 정보가 없습니다.

잘못된 전환 1번의 대가가 큽니다. 감지가 바뀌면 \_apply_detected_language(align_att_base.py:173)가 토크나이저 재생성 + 디코더 컨텍스트 리셋 + 경계 오디오 재디코딩(트림) + 문장경계 마커 삽입을 합니다. 즉 순간적으로 애매한 윈도우(한국어 억양의 영어 고유명사, "um" 같은 filler)에서 거짓 언어 뒤집힘이 나면 디코더 문맥을 통째로 버리고 재디코딩 → churn·filler 환각·과분할. 자주 체크할수록 이 거짓 뒤집힘 기회만 늘어납니다. (그래서 line 235에 전환 직후 3.0s 쿨다운도 있습니다.)

RTF 비용 — 매 체크가 인코더 forward pass 1회라, 0.1s 간격이면 실시간 디코딩과 GPU를 40배 더 다툽니다.

실측이 이걸 뒷받침합니다: 더 촘촘한 PLC=2.0은 과거 3회 전부 기각됐고(Exp-131 bong1 max +9.7pp, Exp-145 전 파일 median 악화), 재감지를 더 공격적으로 한 Exp-137(frame50+PLC4.0)은 bong1 max 55→67% 환각 폭주를 냈습니다. 반대로 4.0은 전환세금을 제거한 뒤(Exp-153) 재평가에서 처음 채택됐습니다(Exp-154: ytn2 median -2.7pp, filler 소멸).

정직한 결론: 네, 4.0은 하드코딩된 휴리스틱 맞습니다. 하지만 "더 잘게 = 더 정확"은 성립하지 않습니다 — 윈도우가 이미 감지 하한을 정하고, 촘촘함은 거짓 뒤집힘·재디코딩 비용만 키웁니다. 4.0은 "연속 발화에서 최대 몇 초까지 틀린 언어로 디코딩하는 걸 감내하나"의 답입니다. 더 원리적인 대안은 타이머가 아니라 디코더 자체 신호(perplexity 급증 등)로 전환을 감지하는 이벤트 기반인데 — 실은 앞의 3개 이벤트 트리거가 이미 그 역할이고, PLC는 그 사이 빈틈만 메우는 하이브리드입니다. (디코더 신뢰도로 전환을 잡는 방향은 단계4에서 프로브했으나 NO-GO였습니다 — Q4 뒤 참조.)

2. QualityGate가 멀쩡한 한국어를 쓰레기로 오해하는지 어떻게 검증했나
   검증 방식 = 버려진 텍스트를 직접 로깅해서 정답과 대조·분류했습니다(추론이 아니라 전수 감사).

원래 QualityGate 로그는 logprob 수치만 남기고 버린 텍스트는 안 남겼습니다 — 그래서 "정상 한국어 vs 환각" 구분이 불가능했습니다. Exp-154 위생 하니스에서 align_att_base.py:566-567에 억제 텍스트를 함께 로깅하도록 고쳤습니다:

text = self.tokenizer.decode(hypothesis).strip()
logger.warning("[QualityGate] avg_logprob %.3f < %.3f — suppressing: %.200s", avg_lp, lp_thr, text)
그다음 경로 C를 재측정 → .omc/server_logs의 억제 텍스트 전수(bong1 46·ytn2 33·sbs1 14)를 정답 스크립트와 대조·분류했습니다. 결과: 전부 ① 비음성 마커(laughter/applause/speaking/AUDIO) ② 문장부호·단일문자 ③ 최종 전사에 이미 존재하는 중복 재디코딩 조각 ④ 환각 조각 — 이 넷 중 하나였고, 정상 한국어가 유실된 건 0건이었습니다. 특히 ③이 많다는 게 핵심입니다: "억제"해도 그 내용은 전사 다른 곳에 이미 있어서 WER에 영향이 없습니다.

"그럼 현재 모델은 이런 케이스가 없다고 해석하면 되나?" — 절반만 맞습니다. 조건을 정확히 붙여야 합니다:

이 감사는 테스트셋(bong1/ytn2/sbs1), E4 코드, CRT=3.0, logprob=-2.0이라는 특정 측정 조건에서 부당드롭 = 0%였다는 경험적 결과입니다. "어떤 경우에도 절대 없다"는 정리(theorem)가 아닙니다.
애초에 의심 자체는 정당했습니다 — "한국어는 logprob 분포가 달라서 −2.0 임계가 과할 수 있다"는 게 가설이었습니다. 감사가 발견한 건 "그 실패 모드가 −2.0 임계·이 데이터에서는 발현되지 않는다"입니다. 임계를 더 낮추거나(−1.0/−1.5는 실제로 sbs1을 터뜨렸습니다 — Exp-140/141) 다른 데이터에서는 정상 한국어가 드롭될 수 있습니다.
부수 성과: ytn2 회차 분산의 근인으로 QualityGate 과억제를 의심했는데, 감사로 **"나쁜 회차의 추가 드롭도 전부 중복·garbage였다"**가 밝혀져 → 분산 근인은 QualityGate가 아니라 재디코딩 churn·ForeignLang 혼란·실오인식으로 재규명됐습니다.
즉 **"현재 임계·현재 데이터에서 이 실패 모드의 증거가 없다 → 언어별 임계나 드롭→재디코딩 수정 불필요"**가 정확한 해석입니다(그래서 사용자 확인 후 단계 C 수정을 안 했습니다). "모델이 구조적으로 이 실수를 못 한다"는 아닙니다.

3. 화자전환 조건부 리셋 — 내용은 타당해 보이는데 왜 악화됐나
   이게 가장 교훈적입니다. **가설은 "Sortformer 과분할이 sbs1 문장분리 F1을 망친다 → 화자전환인데 언어가 같으면 리셋을 생략해 문맥 연속성 보존"**이었습니다. 두 가지 이유로 실패했는데, 둘 다 가설 자체의 오진이었습니다:

① 타겟(sbs1)에서는 코드가 아예 안 돌았습니다. Sortformer가 sbs1에 ChangeSpeaker 이벤트를 0회 생성 → new_speaker가 한 번도 안 불림 → 조건부 리셋 코드에 진입조차 안 함(0/0). sbs1 F1 +12.6은 변경과 무관한 순수 N=1 변산이었습니다. ⇒ sbs1의 F1 급락은 화자전환 리셋이 원인이 아닙니다. 진짜 원인은 tokens_alignment의 문장경계 온점 과분할(전혀 다른 메커니즘)이었습니다. 고치려던 대상의 원인을 잘못 짚었습니다.

② 실제로 발동한 곳(bong1)에서는 오히려 악화됐습니다. bong1은 new_speaker 15회 전부(15/15) 언어가 같아 전부 리셋을 생략했는데 — bong1은 **진짜 화자 4명(영어2·한국어2)**입니다. "언어가 같은 화자전환"은 곧 두 영어 화자 사이, 또는 두 한국어 화자 사이의 진짜 전환입니다. 이걸 "언어가 같으니 과분할이겠지"라며 리셋을 생략하니 → 진짜 다른 사람의 디코더 문맥을 하나로 뭉개버림 → WER +1.8, F1 −4.1.

"타당해 보이는데 아닌" 근본 이유: 이 설계는 **"같은 언어 화자전환 = 억제해야 할 spurious 과분할"**이라고 가정했습니다. 그러나 **"같은 언어" ≠ "spurious"**입니다. 다른 사람이 둘 다 한국어를 말하는 건 목소리·화제·문맥이 끊기는 진짜 화자전환이고, 그 문맥을 병합하면 손해입니다. 언어 일치는 "이 화자전환이 진짜냐 인공물이냐"를 가르는 유효한 신호가 아닙니다. 이건 Exp-106(2.0s 디바운스가 진짜 전환까지 늦춘 기각)과 동형의 함정입니다 — 거친 신호(시간 디바운스 / 언어 일치) 하나로 진짜·가짜 이벤트를 구분하려다 둘 다 잡아버립니다.

정리하면: 과분할이 실제로 F1을 해치는 파일(sbs1)에선 메커니즘이 발동조차 안 했고(오진), 발동한 파일(bong1)에선 진짜 다화자 문맥을 잘못 병합했습니다. N=3 갈 필요도 없이 전제가 반증돼 기각했습니다.

4. 2-pass 프로브 — 상세 동작
   당신의 이해가 큰 틀에서 맞습니다: "1차로 대충 전사 → 중요 구간만 2차 재전사"입니다. 다만 두 가지를 정확히 해야 합니다.

① "중요 구간" = 확정(finalized)된 세그먼트. 실시간이라 아직 확정 안 된 구간은 지연이 생명이라 손댈 수 없습니다. 문장이 확정된 순간(지연이 더는 문제 안 되는 시점)에만 그 구간 PCM을 링버퍼에서 꺼내 재전사하고, validated 세그먼트를 교체합니다.

② "더 좋은 모델"이 아니라 "같은 모델 + 더 좋은 디코딩 알고리즘"입니다. 이게 중요합니다:

1차(live): 스트리밍 디코더 SimulStreaming/AlignAtt — 저지연을 위해 토큰을 점진 커밋하고, 구두점 없고, 문맥이 부분적입니다. 품질을 지연과 맞바꿉니다.
2차(offline): 동일 가중치(whisper-large-v3-turbo)로 표준 whisper.transcribe()를 돌립니다 — 30초 전체 윈도우 + beam search로 세그먼트를 한 번에 통째로 봅니다. 모델이 더 큰 게 아니라, 비스트리밍·전체문맥 디코딩이라 스트리밍이 흘린 걸 복구합니다(원래 Exp-001에서 스트리밍이 영어 블록을 통째 누락한 문제).
왜 "프로브 먼저"인가 — major 방향 전환이라 자율 착수 금지(사용자 합의 필수)이기 때문입니다. 구현하려면 audio_processor에 PCM 링버퍼 신설(현재 PCM은 소비 후 폐기) + 스레딩 + 세그먼트 교체 로직이 필요합니다. 그 큰 배관을 짓기 전에 프로브 3개로 리스크를 뗍니다:

프로브 질문 상태
2a RTF 마이크로벤치 오프라인 재전사가 계산 예산에 들어가긴 하나? ✅ 실행·통과
2b 동시 경합 live AlignAtt+Sortformer와 동시에 돌릴 때 live RTF 열화·peak VRAM은? ⏳ 미실행 (합의 대기)
2c 언어 recall language=auto 오프라인 재전사가 실제로 코드스위칭을 복구하나? ⏳ 미실행 (합의 대기)
2a 결과(단독 측정): ytn2 15/30/45s 버퍼를 large-v3-turbo·beam=2로 오프라인 디코딩 → worst RTF 0.128(30초 오디오 재전사에 ~3.8s = 실시간의 12.8%), peak VRAM 3.5GB(길이 무관). 게이트 RTF<0.5 → 통과. 즉 오프라인 재전사는 실시간 예산의 1/41/8이라 live와 병행할 여유가 있습니다.

단, 2a 통과 = 2b 통과가 아닙니다. 2a는 격리 측정입니다. 진짜 질문은 2b — live 디코딩 + Sortformer가 GPU를 쓰는 와중에 재전사를 얹었을 때 live 지연이 얼마나 무너지느냐입니다. 그리고 2c — 그렇게 해서 얻는 게 실제로 코드스위칭 복구냐. 이 둘 + 본 구현은 모두 사용자 합의 대기 상태입니다(부모 문서 §7).

참고로 단계4(token-logprob 게이트)가 방금 이 앞에서 NO-GO 났는데, 그게 2-pass 동기와 연결됩니다: per-token logprob으로 환각을 걸러내려 했으나, 코드스위칭 정상 단어(holding -17.4, protagonist -15.5)가 garbage(LAUGHS -17.5)와 logprob이 완전히 겹쳐 임계로 못 가릅니다. 즉 "신뢰도로 나쁜 토큰 골라내기"가 이 환경에선 불가 → 남은 방향이 **아예 통째로 다시 전사(2-pass)**입니다.

네 방법 모두 하드코딩/휴리스틱 요소가 있는 건 맞고, 그중 조건부 리셋(3)은 전제가 틀려 기각, token-logprob(4 앞단)은 물리적으로 분리 불가라 NO-GO, PLC(1)·QualityGate(2)는 "더 정교하게 vs 실측 근거"를 대조해보면 현재 값이 방어됩니다. 이 중 더 파고들고 싶은 지점이 있으면 짚어주세요 — 예컨대 PLC를 이벤트 기반으로 바꾸는 방향이나, 2b/2c 프로브 착수는 논의해볼 만합니다.
